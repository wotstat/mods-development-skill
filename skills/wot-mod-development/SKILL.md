# Разработка модов World of Tanks и «Мир танков»

Помогай как начинающим авторам, так и опытным разработчикам. Подстраивай глубину объяснений под пользователя, но не ослабляй требования к доказательствам.

## Обязательный gate по наличию исходного кода

При первом входе в проект, до реализации, исправления или диагностики кода, связанного с API клиента:

1. Установи цель: продукт (`World of Tanks` от Wargaming или «Мир танков» от Lesta), регион и, если доступны, версия и номер билда клиента.
2. Найди доступный локально checkout [`wotstat/wot-src`](https://github.com/wotstat/wot-src) и проверь, что выбрана data-ветка нужного продукта/региона, а не служебная `main`, и что в ней действительно есть нужные client/common исходники. Это обязательное условие.
3. Сопоставь data-ветку, `.publication.json`, commit SHA и версию исходников с клиентом. Точное совпадение повышает уверенность, но расхождение версии само по себе не блокирует работу.
4. Зафиксируй использованные пути к файлам и символы. Документация объясняет подход, но сигнатуры, события, импорты и точки хуков подтверждай по соответствующему checkout исходников.

Для универсального мода нужны исходники каждого заявленного продукта. Checkout от старого патча допустим по правилам сопоставления версий ниже; checkout только одной игры нельзя считать исходниками второй игры.

Повторно используй установленный контекст проекта в следующих итерациях. Перепроверяй gate при смене клиента, продукта, checkout или признаках несовместимости; не запускай полный intake и инспектор после каждой правки.

Если исходников нет или в них отсутствуют необходимые script roots, останови game-coupled реализацию для этой игры и помоги получить код.

В пределах одной мажорной версии расхождение `wot-src` с версией клиента, полученной через файловую систему (`version.xml`) или WotStat REPL MCP, некритично: минорный патч, микропатч и другой build не требуют отдельного предупреждения, понижения уверенности или дополнительных проверок только из-за номера версии. Продолжай работу с доступными исходниками без ожидания обновления `wot-src`, поиска точного snapshot и обсуждения расхождения с пользователем. Обычные проверки мода сохраняются; исследуй совместимость адресно, если есть конкретные признаки изменения используемого API.

При расхождении мажорной версии тоже продолжай работу, но явно сообщи расхождение, понизь уровень уверенности и усили runtime-проверку. Не выдавай непроверенный результат за подтверждённую совместимость с текущим патчем.

Перед такой работой прочитай [evidence-and-intake.md](references/evidence-and-intake.md). При наличии Python 3 можно запустить read-only инспектор:

```bash
python3 <skill-dir>/scripts/inspect_environment.py <project-root> \
  --source <wot-src> \
  --game-dir <game-root> \
  --expected-source-branch <data-branch>
```

## Документация для агента

Начинай навигацию по документации с [`llms.txt`](https://docs.wotstat.info/llms.txt): выбери по индексу релевантные разделы и загрузи их прямые `.md`-страницы. [`llms-full.txt`](https://docs.wotstat.info/llms-full.txt) используй только для сквозного поиска по нескольким разделам, подготовки офлайн-контекста или когда точечные страницы недоступны; не загружай весь bundle по умолчанию. Русская документация является основной.

Документация объясняет концепции и workflow, но может отставать в update-sensitive деталях. Клиентские API подтверждай по целевой data-ветке `wot-src`, runtime-поведение — через клиент/WotStat REPL, а версии инструментов и актуальные ссылки — по первичным README/releases. При конфликте явно укажи расхождение и следуй более свежему первичному источнику.

## Маршрутизация

Сначала изучи доступные файлы проекта и не спрашивай то, что можно определить локально.

- Новый или пустой проект: прочитай [greenfield.md](references/greenfield.md).
- Существующий мод, новый патч, баг или новая функция: прочитай [existing-project.md](references/existing-project.md).
- Любой Python-мод: прочитай [python-mods.md](references/python-mods.md).
- Есть `.as`, `.swf`, `as3/` или Scaleform: дополнительно прочитай [scaleform-as3.md](references/scaleform-as3.md).
- Есть HTML/CSS/JS, `res_map`, Gameface, Wulf GF или Unbound: дополнительно прочитай [gameface.md](references/gameface.md).
- Нужно запустить клиент, выполнить probe, прочитать лог, снять скриншот или провести управляемый UI smoke-тест: прочитай [runtime-validation.md](references/runtime-validation.md).

Если это resource-only мод, прицел, звук, текстура или ремоделинг, не навязывай Python-архитектуру. Определи формат по проекту и соответствующим разделам [`llms.txt`](https://docs.wotstat.info/llms.txt), затем зафиксируй, насколько версии доступных ресурсов и клиента расходятся.

## Рабочий цикл

При первом входе определи цель, доступный `wot-src`, toolchain, команду сборки и доступность REPL; IDE настраивай для нового проекта или по запросу. На следующих итерациях используй уже найденные пути, API и команды. Перечитывай документацию и исследуй исходники адресно: для нового/изменяемого контракта или конкретного сбоя, а не для повторного доказательства неизменившегося кода.

Обычная итерация должна быть короткой:

1. **Внеси минимальную правку.** Следуй структуре проекта. Новый игровой API подтверди по `wot-src`; известный неизменившийся контракт используй повторно.
2. **Выполни существующую сборку.** Она компилирует Python 2.7, собирает UI при необходимости и выдаёт пакет. Не дублируй успешную компиляцию отдельным syntax-check и не меняй pipeline ради обычной правки мода.
3. **Отдай результат или проверь в REPL.** Если пользователь просит только сборку либо клиент/REPL недоступен, верни артефакт и кратко отметь отсутствие runtime-проверки. При доступном REPL самостоятельно проверь изменённый сценарий в рамках задачи. Для быстрой проверки логов читай последние N записей через REPL; для большого поиска используй `python.log` в корне игры, не вычитывай историю по cursor. Не останавливайся с предложением «могу проверить». Убедись, что клиент исполняет обновлённый код, по [runtime-validation.md](references/runtime-validation.md).
4. **Заверши или исправь конкретный сбой.** После успешной целевой проверки отдай результат. Если она не прошла, внеси минимальное исправление и повтори затронутую проверку.

Полную проверку окружения, IDE, чистоты сборки и inventory пакета повторяй при изменении соответствующих настроек, build path, состава/путей ресурсов или при связанном сбое. Lifecycle, повторное открытие, разные разрешения и оба продукта проверяй, когда правка затрагивает эти свойства либо заявляешь готовность релиза/миграции; не запускай всю матрицу на каждой промежуточной итерации. Не создавай планы, таблицы доказательств, отчёты и вспомогательные скрипты для обычной правки без необходимости задачи.

Предпочитай существующие события и точки расширения; соблюдай правила подмены ресурсов ниже. Если нужен monkey patch, сохраняй оригинал, аргументы, возвращаемое значение и порядок вызова; установка должна быть идемпотентной. Не скрывай исключения широким `except`.

Сокращай объём тестов до полезного минимума. Не подстраивай архитектуру мода под тесты: не вводи дополнительные слои, dependency injection или моки BigWorld/gui и других объектов клиента только ради unit-тестирования. Это усложняет код и мало говорит о поведении в игре. Для интеграции с клиентом предпочитай несколько целевых проверок на реальном клиенте через WotStat REPL большой коллекции unit-тестов; подробности — в [python-mods.md](references/python-mods.md#чистая-логика-и-тесты).

Держи сборку короткой и линейной: копирование в staging → версия → компиляция → упаковка. Адаптируй пример из документации по [greenfield.md](references/greenfield.md#сборка-и-pipeline); не создавай сборочный фреймворк. Проверки чистоты исходников и содержимого архива выполняй как агент при проверке результата, не превращая их в инфраструктуру build-скрипта. Сохраняй существующую сборку, если она подходит задаче.

Для нового code-мода настройка IDE является отдельным критерием готовности: успешная release-сборка не доказывает, что language server видит собственные исходники, целевой `wot-src`, stubs или AS3 libraries. Проверь representative-файлы Python и выбранного UI-стека в самом редакторе по правилам из [greenfield.md](references/greenfield.md), [python-mods.md](references/python-mods.md) и [scaleform-as3.md](references/scaleform-as3.md).

## Совместимость и подмена игровых ресурсов

Замена существующих файлов игры крайне нежелательна: она создаёт высокий риск конфликтов с другими модами, изменяющими тот же ресурс. По умолчанию реализуй изменения через точки расширения, отдельные ресурсы мода с уникальными путями и минимальные runtime-патчи. Подменой считается не только перезапись файла в установленной игре, но и перекрытие штатного виртуального пути через `res_mods`, `.wotmod`/`.mtmod` или другой механизм загрузки ресурсов. То, что оригинал на диске не изменён, не устраняет риск несовместимости.

Если пользователь явно попросил заменить конкретный игровой файл/ресурс, это разрешение на указанную подмену; предупреди о риске конфликтов и не расширяй её на другие файлы. Просьба изменить внешний вид или поведение сама по себе не является просьбой подменить файл.

Если явного запроса на подмену нет, сначала ищи решение без неё. Если без подмены обойтись нельзя, **до её реализации остановись и получи явное согласие пользователя**: назови файлы/виртуальные пути, объясни, почему альтернативы не подходят, и предупреди о риске нарушения совместимости с другими модами. Дедлайн, уже подготовленный заменяющий файл или простота подмены не заменяют согласие. Правило действует и для resource-only модов.

При проверке пакета ищи непреднамеренные совпадения путей с ресурсами игры; каждая намеренная подмена должна входить в согласованный scope. Runtime-патчи также проверяй на взаимодействие с другими модами: отсутствие подмены файла само по себе не гарантирует совместимость.

## Отношение к существующему проекту

Для нового Python-мода рекомендуй стиль клиента по умолчанию: классы — `PascalCase`, функции, методы, параметры, переменные и свойства — `camelCase`, константы — `UPPER_SNAKE_CASE`, модули и пакеты — `snake_case`. Подробности — в [python-mods.md](references/python-mods.md#стиль-именования).

В существующем моде его соглашения имеют приоритет над этим стилем по умолчанию: новый и изменяемый код должен быть консистентен с окружающим кодом мода.

Сохраняй принятые в проекте структуру, naming, сборку и стиль, если они не блокируют задачу. Не превращай добавление функции или перенос патча в незапрошенный рефакторинг. Если нужен seam, вводи его вокруг меняющегося API минимальным патчем.

Не изменяй `wot-src` и извлечённые SWC; исходные игровые ресурсы сохраняй как read-only эталон. Согласованную подмену готовь в отдельных файлах мода, а не правкой эталона. Не включай исходники, SWC или игровые ресурсы в артефакт и не коммить без явно подтверждённого права на распространение; согласие на подмену не подтверждает такое право.

## Критерий готовности

Для обычной итерации достаточно коротко указать изменение, путь к артефакту и результат проверки: собрано; проверено в клиенте; либо runtime не проверен. Не выдавай успешную компиляцию за подтверждение поведения. Запрос только на сборку завершён после получения артефакта; недоступность клиента не требует имитировать его тестами.

Продукт, регион, source data-branch/SHA и ключевые исходные символы фиксируй при первом исследовании, смене цели или в отчёте о миграции/совместимости. Не повторяй неизменившийся паспорт окружения в каждом ответе. О существенных новых расхождениях и ограничениях сообщай явно.

Для изменений боевого интерфейса используй реплей, тренировочную комнату, тестовый сервер или «Полигон», а не случайный бой.
