# Новый мод: greenfield workflow

Читайте этот файл для пустого проекта или когда пользователь явно просит новое основание архитектуры.

## Работа с начинающим автором

Не превращайте intake в экзамен. После локальной проверки кратко сформулируйте понятную карточку: что мод делает, где это видно, для какой игры/версии и нужен ли UI. Если идея слишком широкая, выберите вместе минимальный вертикальный срез с наблюдаемым результатом.

Пока source gate заблокирован из-за отсутствия пригодных исходников, не генерируйте игровые импорты, события или hooks. Version warning не запрещает работу, но должен быть виден пользователю.

## Naming

Выберите один стабильный набор идентификаторов и используйте его везде:

- distribution/mod id: уникальный lowercase id наподобие `author.mod-name`;
- Python package: уникальный `author_mod_name` в snake_case;
- loader entry: `mod_author_mod_name.py`, если доступный source подтверждает соглашение `mod_*.py`; при несовпадении версии перепроверьте loader в runtime;
- log prefix: короткий уникальный `[AUTHOR_MOD_NAME]`;
- Gameface `itemID`, linkage настроек и event names: с тем же уникальным namespace.

Не используйте глобально-конфликтные имена вроде `main`, `common`, `utils` или `config` вне собственного package. Не переименовывайте опубликованный id без плана миграции настроек и зависимостей.

## Минимальная архитектура

Начинайте неглубоко и добавляйте уровни только для существующих обязанностей:

```text
project/
├── meta.xml
├── build.bat
├── build.sh                         # если нужен Linux/CI
├── .github/workflows/release.yml    # если запрошена публикация
├── .vscode/settings.json
├── .vscode/extensions.json
├── res/scripts/client/gui/mods/
│   ├── mod_author_mod_name.py       # тонкая loader-owned точка входа
│   └── author_mod_name/
│       ├── __init__.py
│       ├── bootstrap.py             # install/lifecycle
│       └── feature.py               # первый вертикальный срез
└── tests/                            # только реально тестируемая чистая логика
```

Не создавайте пустые `services/`, `repositories/`, `interfaces/` и другие слои «на будущее».

Точка входа должна делать минимум: объявить версию/metadata в принятой проектом форме и передать управление bootstrap. Game logic, UI и конфиг держите в namespaced package. Подтвердите по source loader, вызывает ли он `init()`, импортирует мод ради side effects или использует другой контракт.

Bootstrap владеет установкой подписок/patches и должен защищаться от двойной установки. Если lifecycle предоставляет симметричную очистку, снимайте подписки и восстанавливайте patches. Не выдумывайте unload API, которого нет в исходниках.

## Архитектура universal-мода

Сначала реализуйте общий, не зависящий от клиента смысл функции. Добавляйте compatibility seam только там, где source diff доказал расхождение:

```text
author_mod_name/
├── bootstrap.py
├── feature.py
└── compat/
    ├── __init__.py
    ├── lesta.py
    └── wargaming.py
```

Не дублируйте весь мод по продуктам. Не определяйте продукт по случайному исключению. Используйте устойчивый capability/identity signal, найденный в обоих наборах исходников, и явно падайте с понятным логом на неподдержанной версии.

## IDE readiness gate

Для нового code-мода editor setup входит в definition of done. Не считайте окружение настроенным, пока representative-файлы каждого используемого языка действительно открываются с рабочими переходами к определениям, hover и completion, а в Problems/Output нет системных ошибок о неразрешённых source roots, SDK, libraries или entry class.

При настройке VS Code:

1. объединяйте настройки с существующими файлами, не перезаписывая пользовательскую конфигурацию целиком;
2. добавляйте `.vscode/extensions.json` с `ms-python.python` и `ms-python.vscode-pylance`, а для AS3 — также `bowlerhatllc.vscode-as3mxml`;
3. не коммитьте абсолютные пользовательские пути: используйте `${workspaceFolder}`, относительные пути, переменные проекта либо документированный локальный override;
4. для universal-мода предпочтительно создавайте отдельные MT/WoT `.code-workspace`-профили, каждый с одним целевым checkout; если используется один профиль, явно задайте приоритет единственного активного snapshot;
5. дождитесь индексации и проверьте собственный Python import, игровой модуль из `client/common/client_common` и нативный модуль из `stubs` на representative-файле;
6. если есть AS3, проверьте `flash.*` и игровые `net.wg.*` symbols, затем соберите тот же target через `asconfig.json` с помощью `asconfigc` или VS Code Quick Compile;
7. отдельно выполните release-сборку и проверьте её артефакт.

Рекомендация расширения не доказывает, что оно установлено и запущено. Статическая проверка конфигов также не заменяет просмотр Problems и language-server Output в реальном редакторе. Успешная сборка через `build-config.xml` не доказывает исправность VS Code: расширение AS3 читает `asconfig.json`.

Не требуйте буквально нулевого числа diagnostics: legacy Python 2, неполные native stubs и декомпилированные игровые исходники могут давать локальный ожидаемый шум. Зафиксируйте такие исключения отдельно; массовые missing imports/types или неразрешённые SDK/SWC означают, что gate не пройден.

В существующем проекте не переписывайте IDE-конфигурацию без необходимости. Но если пользователь просит настроить окружение или diagnostics мешают задаче, проверьте её тем же gate и либо исправьте, либо явно сообщите, что осталось непроверенным.

## Сборка и pipeline

Ориентир по базовой упаковке: <https://docs.wotstat.info/guide/first-steps/environment/python/index.md>. Для CI: <https://docs.wotstat.info/guide/first-steps/automatization/index.md>.

Сборка должна:

1. принимать версию явно и проверять формат;
2. работать в отдельном build-каталоге;
3. компилировать Python именно совместимым Python 2.7 interpreter;
4. при необходимости собирать UI;
5. подставлять одну и ту же версию в entry/meta;
6. включать только разрешённые runtime-файлы с правильными путями;
7. падать при любой ошибке компилятора, отсутствующем entry/meta или пустом результате;
8. проверять содержимое готового `.wotmod`/`.mtmod`, а не только exit code архиватора;
9. не включать `wot-src`, исходные `.py`, SWC, логи, secrets и локальные пути, если формат релиза этого не требует.

Для локальной Windows-сборки допустим `build.bat`; для GitHub Actions нужен Linux-compatible путь. Не копируйте workflow вслепую: закрепляйте версии actions/компиляторов, выдавайте минимальные permissions и публикуйте release только по однозначному tag trigger. Сетевые и публикационные действия выполняйте только в запрошенном scope.

## Первая проверяемая версия

Сначала добейтесь следующей цепочки:

```text
доступный source + version warning → Python 2 compile → package layout → загрузка entry → уникальный log marker
```

Затем добавьте одну безопасную пользовательскую функцию. Для боевой функции сначала проверьте её на replay/тренировочном сценарии. Только после этого расширяйте UI, настройки и pipeline.
