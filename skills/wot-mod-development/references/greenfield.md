# Новый мод: greenfield workflow

Читайте этот файл для пустого проекта или когда пользователь явно просит новое основание архитектуры.

## Работа с начинающим автором

Если идея слишком широкая, выберите вместе минимальную функцию с наблюдаемым результатом. Наличие исходников и выбор цели проверяйте по [SKILL.md](../SKILL.md).

## Naming

Выберите один стабильный набор идентификаторов и используйте его везде:

- distribution/mod id: уникальный lowercase id наподобие `author.mod-name`;
- Python package: уникальный `author_mod_name` в snake_case;
- loader entry: `mod_author_mod_name.py` с функцией `init()` в обоих продуктах;
- log prefix: короткий уникальный `[AUTHOR_MOD_NAME]`;
- Gameface `itemID`, linkage настроек и event names: с тем же уникальным namespace.

Не используйте глобально-конфликтные имена вроде `main`, `common`, `utils` или `config` вне собственного package. Не переименовывайте опубликованный id без плана миграции настроек и зависимостей.

## Минимальная архитектура

Начинайте неглубоко и добавляйте уровни только для существующих обязанностей:

```text
project/
├── .gitignore
├── meta.xml
├── build.bat
├── build.sh                         # если нужен Linux/CI
├── .github/workflows/release.yml    # если запрошена публикация
├── .vscode/settings.json
├── .vscode/extensions.json
├── res/scripts/client/gui/mods/
│   ├── mod_author_mod_name.py       # тонкая loader-owned точка входа
│   └── author_mod_name/
│       ├── __init__.py
│       ├── bootstrap.py             # install/lifecycle
│       └── feature.py               # первый вертикальный срез
└── tests/                          # необязательно: немного полезных тестов самостоятельной логики
```

Не создавайте пустые `services/`, `repositories/`, `interfaces/` и другие слои «на будущее».

Точка входа должна делать минимум: объявить версию/metadata в принятой проектом форме и передать управление bootstrap из `init()`. Game logic, UI и конфиг держите в namespaced package.

Bootstrap владеет установкой подписок/patches и должен защищаться от двойной установки. Если lifecycle предоставляет симметричную очистку, снимайте подписки и восстанавливайте patches. Не выдумывайте unload API, которого нет в исходниках.

## Архитектура universal-мода

Сначала реализуйте общий, не зависящий от клиента смысл функции. Добавляйте compatibility seam только там, где source diff доказал расхождение:

```text
author_mod_name/
├── bootstrap.py
├── feature.py
└── compat/
    ├── __init__.py
    ├── lesta.py
    └── wargaming.py
```

Не дублируйте весь мод по продуктам. Не определяйте продукт по случайному исключению. Используйте устойчивый capability/identity signal, найденный в обоих наборах исходников, и явно падайте с понятным логом на неподдержанной версии.

## IDE readiness gate

Для нового code-мода editor setup входит в definition of done. Не считайте окружение настроенным, пока representative-файлы каждого используемого языка действительно открываются с рабочими переходами к определениям, hover и completion, а в Problems/Output нет системных ошибок о неразрешённых source roots, SDK, libraries или entry class.

При настройке VS Code:

1. объединяйте настройки с существующими файлами, не перезаписывая пользовательскую конфигурацию целиком;
2. добавляйте `.vscode/extensions.json` с `ms-python.python` и `ms-python.vscode-pylance`, а для AS3 — также `bowlerhatllc.vscode-as3mxml`;
3. не коммитьте абсолютные пользовательские пути: используйте `${workspaceFolder}`, относительные пути, переменные проекта либо документированный локальный override;
4. для universal-мода предпочтительно создавайте отдельные MT/WoT `.code-workspace`-профили, каждый с одним целевым checkout; если используется один профиль, явно задайте приоритет единственного активного snapshot;
5. дождитесь индексации и проверьте собственный Python import, игровой модуль из `client/common/client_common` и нативный модуль из `stubs` на representative-файле;
6. если есть AS3, проверьте `flash.*` и игровые `net.wg.*` symbols, затем соберите тот же target через `asconfig.json` с помощью `asconfigc` или VS Code Quick Compile;
7. отдельно выполните release-сборку и проверьте её артефакт.

Рекомендация расширения не доказывает, что оно установлено и запущено. Статическая проверка конфигов также не заменяет просмотр Problems и language-server Output в реальном редакторе. Успешная сборка через `build-config.xml` не доказывает исправность VS Code: расширение AS3 читает `asconfig.json`.

Не требуйте буквально нулевого числа diagnostics: legacy Python 2, неполные native stubs и декомпилированные игровые исходники могут давать локальный ожидаемый шум. Зафиксируйте такие исключения отдельно; массовые missing imports/types или неразрешённые SDK/SWC означают, что gate не пройден.

В существующем проекте не переписывайте IDE-конфигурацию без необходимости. Но если пользователь просит настроить окружение или diagnostics мешают задаче, проверьте её тем же gate и либо исправьте, либо явно сообщите, что осталось непроверенным.

## Сборка и pipeline

Основа — [пример сборки Python-мода](https://docs.wotstat.info/guide/first-steps/environment/python/index.md) и его [build.bat](https://docs.wotstat.info/download/mod-build/build.bat). Адаптируйте его короткую линейную последовательность под конкретный мод:

1. Задать имя мода, entry и пути к инструментам в небольшом блоке настроек; получить версию аргументом, как `-v 1.0.0`, и проверить допустимый для проекта формат.
2. Пересоздать выделенный `build/` или `.build/` и скопировать туда `res/`. Это staging — рабочая копия для всех преобразований.
3. Заменить `{{VERSION}}` в staged entry и записать туда же `meta.xml` с той же версией.
4. Скомпилировать staged `.py` интерпретатором Python 2.7 в `.pyc`.
5. Если мод содержит UI, вызвать его компилятор и поместить результат в staging по runtime-пути; для AS3 это обычно `res/gui/flash/*.swf`. Для Python-only мода этот шаг отсутствует.
6. Упаковать staged `meta.xml`, `.pyc` и используемые ресурсы в ZIP без сжатия (`7z -tzip -mx=0`) с расширением `.wotmod` или `.mtmod`, сохраняя runtime layout. Список ресурсов задайте по фактическому моду: `.swf` и `.png` из примера не являются исчерпывающим списком.
7. Поместить готовый `имя_версия` пакет в `dist/` и вывести его путь. В примере результат копируется в корень проекта; в существующем проекте сохраняйте принятое расположение.

Достаточно одного скрипта для нужной платформы. Не создавайте сборочный фреймворк, систему задач, универсальные конфиги, автоматический поиск/установку инструментов или поддержку дополнительных платформ без конкретной необходимости. UI-компилятор подключайте только при наличии UI. CI и публикацию добавляйте по запросу; для Linux можно адаптировать [build.sh](https://docs.wotstat.info/download/mod-build/build.sh) из [руководства по автоматизации](https://docs.wotstat.info/guide/first-steps/automatization/index.md).

Сохраняйте две обязательные гарантии: исходники не изменяются, а ошибка останавливает сборку. В учебном `build.bat` нет надёжной остановки после каждой ошибки компиляции/упаковки: добавьте простую проверку результата соответствующей команды, включая результат Python 2 `compileall`; отсутствие обязательного entry/meta или пустой результат также должны завершать сборку с ошибкой.

Python 2 `py_compile`/`compileall` обычно создают `.pyc` рядом с входным `.py`, поэтому компилируйте только staged-копию либо явно задавайте `cfile` внутри staging. Не компилируйте исходный `res/` с последующим удалением `.pyc`. Для AS3 адаптируйте пример с `as3/bin`: output, временные SWC и generated configs направляйте в staging. Исходные `res/`, `as3/src/` и другие author-owned каталоги остаются read-only. Очистку ограничьте выделенным build root; добавьте build/dist roots и Python bytecode в `.gitignore`.

Упаковывайте только runtime-файлы мода; `wot-src`, исходные `.py`, SWC, логи, secrets и локальные пути в обычный релиз не входят.

## Проверка сборки

При создании или изменении сборки проверьте пути inputs/outputs, состав готового архива и отсутствие новых artifacts или изменений в исходниках после запуска. Для сравнения учитывайте исходное состояние проекта, не очищая пользовательские изменения. Проверки выполняет агент; встраивать git-аудит или хеширование исходников в build-скрипт не нужно.

Для простого линейного скрипта достаточно обычной сборки и просмотра путей staging/очистки. Пробу с намеренной ошибкой добавляйте только при сложной очистке или исправлении конкретного бага сохранности исходников; она не обязательна по умолчанию.

Если запрошен CI, выбирайте build path под его runner. Не копируйте workflow вслепую: закрепляйте версии actions/компиляторов, выдавайте минимальные permissions и публикуйте release только по однозначному tag trigger. Сетевые и публикационные действия выполняйте только в запрошенном scope.

## Первая проверяемая версия

Сначала добейтесь следующей цепочки:

```text
доступный source → Python 2 compile → package layout → загрузка entry → уникальный log marker
```

Затем добавьте одну безопасную пользовательскую функцию. Для боевой функции сначала проверьте её на replay/тренировочном сценарии. Только после этого расширяйте UI, настройки и pipeline.
