# Существующий мод и перенос на новый патч

Читайте этот файл для готового проекта, исправления бага, новой функции или адаптации под новую версию клиента.

## Сначала инвентаризация

До изменений определите:

- dirty state и пользовательские изменения;
- существующие entry points, package layout, naming и конфиг;
- локальные/CI build paths и ожидаемое содержимое `.wotmod`/`.mtmod`;
- заявленные продукты и версии;
- UI stack и внешние mod dependencies;
- текущую ошибку, последний успешный патч и способ воспроизведения.

Не исправляйте архитектуру только потому, что предпочли бы другую. Сначала найдите наименьший совместимый change surface. Не форматируйте и не переписывайте несвязанные файлы.

## Диагностика

Разделите проблему по этапу:

1. source/syntax — код не парсится Python 2 или UI-компилятором;
2. build/package — неверный layout, версия или отсутствующий файл;
3. discovery/import — loader не находит entry или импорт падает;
4. lifecycle/API — изменился symbol, signature, event timing или app scope;
5. behavior — мод загружается, но делает не то;
6. rendering — Python model жив, но Scaleform/Gameface не отображается или не обновляется;
7. compatibility — конфликт с другим модом или второй игрой.

Начинайте с первого подтверждённого сбоя, а не с симптома в конце цепочки. Используйте уникальный log prefix и полный traceback. Не очищайте пользовательский лог ради теста; отмечайте cursor/timestamp и читайте только новые строки.

## Patch migration

Зафиксируйте source identities старого рабочего и нового целевого клиента. Точные commits предпочтительны, но ближайший доступный checkout допустим с предупреждением; отсутствие исходников недопустимо. Если старого checkout нет, попробуйте найти его в истории `wot-src` по version/build.

Для каждого используемого игрового symbol:

1. найдите определение и callers в старом commit;
2. сравните тот же участок с новым commit (`git diff <old>..<new> -- <paths>`);
3. проверьте rename/move, signature, return value, lifecycle, scope и соседние игровые реализации;
4. классифицируйте изменение: неизменно, переименовано, изменён контракт, удалено или заменено другим механизмом;
5. обновите только соответствующий adapter/hook и тест.

Не делайте массовую замену имени, пока не проверены семантика и callers. Если API разошёлся между WoT и «Мир танков», зафиксируйте две source-backed ветки compatibility вместо цепочки неясных `try/except ImportError`.

## Добавление функции

Следуйте существующим seams. Если game API уже размазан по feature-коду и это мешает изменению, выделите минимальный adapter вокруг конкретного нестабильного symbol. Не переносите весь проект на новую архитектуру без отдельного запроса.

Перед изменением hook проверьте:

- есть ли event/официальная точка расширения вместо monkey patch;
- сохраняется ли оригинальная сигнатура, `*args/**kwargs` и return value;
- не устанавливается ли patch дважды;
- совместим ли порядок вызова с другими модами;
- что произойдёт при частично инициализированном или уничтоженном объекте.

Ошибки должны содержать feature, product/build и стадию lifecycle. Не продолжайте молча после обязательной неудачной инициализации.

## Проверка регрессий

Соберите пакет тем же способом, которым он публикуется. Проверьте как минимум:

- Python 2 compile всех runtime `.py`;
- отсутствие новых `.pyc`, `.pyo`, `__pycache__`, generated SWC/SWF и изменений tracked-файлов в author-owned source tree после успешной и неуспешной сборки;
- UI compile, если применимо;
- точный список файлов в `.wotmod`/`.mtmod`;
- загрузку без новых traceback/error;
- исходный рабочий сценарий;
- изменённый сценарий;
- каждый заявленный продукт/патч отдельно.

Runtime-проверка нового клиента обязательна для утверждения «адаптировано под патч». Если клиента нет, результат формулируйте как source-backed/build-verified, но runtime-unverified; отдельно укажите, совпадает ли source version.

Если существующий build компилирует Python in-place, исправьте это минимально: перенесите compile/package inputs в staging или задайте явные output paths. Не маскируйте проблему cleanup-командой по исходному `res/` и не удаляйте уже существующие пользовательские artifacts без отдельного согласования.
