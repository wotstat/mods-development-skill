# Runtime validation и WotStat REPL

Читайте при диагностике живого клиента, smoke-тестах, работе с логами, визуальной проверке или настройке MCP.

Рекомендуемый инструмент: [WotStat REPL](https://github.com/wotstat/wotstat-repl). Это desktop IDE и игровой агент для World of Tanks и «Мира танков»: live Python 2.7 REPL в главном потоке клиента, потоковые `stdout`/`stderr`/`BigWorld.log*`, runtime autocomplete с сигнатурами, запуск клиента или реплея и встроенный MCP server.

Runtime-интроспекция дополняет, но не отменяет подходящую data-ветку [`wotstat/wot-src`](https://github.com/wotstat/wot-src): REPL показывает фактический живой объект, а исходники объясняют lifecycle и callers.

## Установка и подключение

Используйте [последний релиз](https://github.com/wotstat/wotstat-repl/releases/latest) и актуальный README. Desktop-приложение доступно для Windows, macOS и Linux. При доступе к локальной установке игры оно само устанавливает встроенный агент; для ручной или удалённой установки релиз содержит `.wotmod` и `.mtmod`.

В status bar откройте **MCP** и добавьте конфигурацию в поддерживаемый агент. WotStat REPL умеет атомарно зарегистрировать `wot_repl` как для Codex/ChatGPT Desktop, так и для Claude Code; CLI для этого не нужен. После добавления или удаления MCP перезапустите агентское приложение. Если автоматическая регистрация недоступна, скопируйте локальный Streamable HTTP URL из UI и следуйте инструкции своего агента.

MCP URL содержит постоянный token. Не копируйте его в issue, commit, ответ, публичный config или сохранённый лог. Для работы на одной машине используйте loopback URL. Открывайте Agent LAN/MCP в сеть только осознанно, с включённой аутентификацией и подходящими firewall rules. REPL выполняет произвольный код внутри игры, поэтому не предоставляйте доступ недоверенным пользователям.

Web REPL на `127.0.0.1:8768` подходит для ручных команд, логов, диагностики и autocomplete без desktop UI, но не предоставляет MCP, управление процессом или сетевые настройки.

## Сначала определите capabilities

Не предполагайте одинаковый набор tools на всех платформах. Сверяйте реально опубликованную MCP schema перед каждым workflow.

Полный профиль Windows-приложения, работающего на одной машине с игрой, предоставляет:

| Tool | Назначение |
| --- | --- |
| `wot_list_clients` | Показать локальные установки и capabilities |
| `wot_start_client` | Установить/подключить агент и запустить клиент или replay |
| `wot_close_client` | Корректно закрыть активный локальный клиент |
| `wot_kill_client` | Принудительно завершить проверенный игровой процесс |
| `wot_exec` | Выполнить Python 2.7-код в главном потоке игры |
| `wot_read_log` | Читать свежие log records по cursor, при необходимости с коротким ожиданием |
| `wot_screenshot` | Получить JPG/PNG игрового окна как MCP image content |
| `wot_mouse` | Управлять виртуальным игровым курсором, кнопками и колесом |
| `wot_keyboard` | Отправлять виртуальные key down/up/press во входной pipeline игры |

Удалённый профиль macOS/Linux намеренно публикует только `wot_exec`. Это не ошибка подключения: поиск/запуск/завершение клиента, логи, screenshot и input требуют Windows-приложение рядом с игрой. MCP-клиент при этом может подключаться к этому Windows-приложению по разрешённой сети и получить полный профиль.

## Безопасный capability-driven цикл

1. Зафиксируйте target product, region, version и game path. Если доступен `wot_list_clients`, выберите клиент по явному пути/capabilities, а не по позиции в списке.
2. Если доступен `wot_read_log`, получите baseline cursor; не очищайте пользовательский лог. Иначе зафиксируйте timestamp/позицию файла доступным read-only способом.
3. Подключитесь к уже запущенному клиенту или вызовите `wot_start_client` для явно выбранного клиента/replay. Не запускайте и не закрывайте чужую сессию без необходимости задачи.
4. Сопоставьте реально запущенную версию с data-веткой/SHA `wot-src`. Mismatch — предупреждение, а не автоматическая остановка теста.
5. Сначала выполните короткий read-only `wot_exec` probe: импорт, наличие symbol, тип, `__doc__`/signature и lifecycle state.
6. Соберите и установите тестовый `.wotmod`/`.mtmod` обычным workflow проекта. Установка REPL agent не устанавливает пользовательский мод.
7. Для визуального сценария при наличии `wot_screenshot` сохраните baseline, выполните одно ограниченное действие и снимите результат. Не делайте вывод по одному изображению без проверки логов/state.
8. Используйте `wot_mouse`/`wot_keyboard` только для согласованного воспроизводимого теста в меню, replay, тренировочной комнате, тестовом режиме или «Полигоне». Не автоматизируйте gameplay и не отправляйте input в публичном бою.
9. Прочитайте только новые логи по cursor; ищите уникальный mod prefix, traceback, ERROR/WARNING. Повторите после минимального изменения.
10. Закройте локально запущенный для теста клиент через `wot_close_client`, если это входит в scope. `wot_kill_client` используйте только после неудачи graceful close и с учётом потери несохранённого state.

`wot_exec` работает на main thread: не запускайте долгие циклы, blocking I/O, ожидание или тяжёлую обработку. Используйте маленькие probes и ограниченный timeout. Перед input-событием проверьте текущий экран и focus через screenshot/state. Скриншоты могут содержать никнеймы, чат и другие пользовательские данные — не публикуйте их автоматически.

## Что проверять

Минимальный smoke test:

- package обнаружен loader-ом;
- entry завершился без traceback;
- ожидаемые subscriptions/registrations установлены один раз;
- feature выдаёт безопасный наблюдаемый marker;
- после действия нет новых ошибок;
- повторный вход в context не дублирует hook/listener.

Для patch migration добавьте probes изменившихся signatures и lifecycle state. Для Scaleform проверяйте Python registration, создание view и bridge. Для Gameface — resource id, создание view/model, engine readiness, JS/Python command roundtrip и cleanup. Визуальные изменения проверяйте screenshot до/после на нужных разрешениях/UI scale, но состояние модели подтверждайте отдельно.

Предпочитайте replay для воспроизводимости. Если replay недостаточен, используйте тренировочную комнату, тестовый сервер или «Полигон». Записывайте точные шаги, карту/режим и момент ожидаемого поведения, чтобы следующий прогон был сопоставим.

Итоговое утверждение различайте явно:

- **source-backed** — решение основано на доступных исходниках с указанной версией;
- **exact-source-verified** — API подтверждён checkout той же версии/build;
- **build-verified** — compiler и package checks прошли;
- **load-verified** — клиент загрузил мод без новых ошибок;
- **behavior-verified** — целевой runtime scenario наблюдался;
- **visual-verified** — ожидаемое состояние интерфейса подтверждено screenshot и связанным runtime state;
- **cross-product verified** — предыдущие проверки отдельно прошли для каждой заявленной цели.
