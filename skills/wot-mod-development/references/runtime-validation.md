# Runtime validation и WotStat REPL

Читайте при диагностике живого клиента, smoke-тестах, работе с логами, визуальной проверке или настройке MCP.

Рекомендуемый инструмент: [WotStat REPL](https://github.com/wotstat/wotstat-repl). Это desktop IDE и игровой агент для World of Tanks и «Мира танков»: live Python 2.7 REPL в главном потоке клиента, потоковые `stdout`/`stderr`/`BigWorld.log*`, runtime autocomplete с сигнатурами, запуск клиента или реплея и встроенный MCP server.

Runtime-интроспекция дополняет, но не отменяет подходящую data-ветку [`wotstat/wot-src`](https://github.com/wotstat/wot-src): REPL показывает фактический живой объект, а исходники объясняют lifecycle и callers.

## Установка и подключение

Используйте [последний релиз](https://github.com/wotstat/wotstat-repl/releases/latest) и актуальный README. Desktop-приложение доступно для Windows, macOS и Linux. При доступе к локальной установке игры оно само устанавливает встроенный агент; для ручной или удалённой установки релиз содержит `.wotmod` и `.mtmod`.

В status bar откройте **MCP** и добавьте конфигурацию в поддерживаемый агент. WotStat REPL умеет атомарно зарегистрировать `wot_repl` как для Codex/ChatGPT Desktop, так и для Claude Code; CLI для этого не нужен. После добавления или удаления MCP перезапустите агентское приложение. Если автоматическая регистрация недоступна, скопируйте локальный Streamable HTTP URL из UI и следуйте инструкции своего агента.

MCP URL содержит постоянный token. Не копируйте его в issue, commit, ответ, публичный config или сохранённый лог. Для работы на одной машине используйте loopback URL. Открывайте Agent LAN/MCP в сеть только осознанно, с включённой аутентификацией и подходящими firewall rules. REPL выполняет произвольный код внутри игры, поэтому не предоставляйте доступ недоверенным пользователям.

Web REPL на `127.0.0.1:8768` подходит для ручных команд, логов, диагностики и autocomplete без desktop UI, но не предоставляет MCP, управление процессом или сетевые настройки.

## Сначала определите capabilities

Не предполагайте одинаковый набор tools на всех платформах. Проверьте опубликованную MCP schema при первом подключении и используйте её в следующих итерациях; сверяйте заново после изменения подключения/tools или ошибки контракта.

Полный профиль Windows-приложения, работающего на одной машине с игрой, предоставляет:

| Tool | Назначение |
| --- | --- |
| `wot_list_clients` | Показать локальные установки и capabilities |
| `wot_start_client` | Установить/подключить агент и запустить клиент или replay |
| `wot_close_client` | Корректно закрыть активный локальный клиент |
| `wot_kill_client` | Принудительно завершить проверенный игровой процесс |
| `wot_exec` | Выполнить Python 2.7-код в главном потоке игры |
| `wot_read_log` | Быстро прочитать последние N записей; параметры — по доступной MCP schema |
| `wot_screenshot` | Получить JPG/PNG игрового окна как MCP image content |
| `wot_mouse` | Управлять виртуальным игровым курсором, кнопками и колесом |
| `wot_keyboard` | Отправлять виртуальные key down/up/press во входной pipeline игры |

Удалённый профиль macOS/Linux намеренно публикует только `wot_exec`. Это не ошибка подключения: поиск/запуск/завершение клиента, логи, screenshot и input требуют Windows-приложение рядом с игрой. MCP-клиент при этом может подключаться к этому Windows-приложению по разрешённой сети и получить полный профиль.

## Подключение и короткий цикл

При первом подключении определите target product, region, version и game path. Если доступен `wot_list_clients`, выбирайте клиент по явному пути/capabilities. Сопоставьте его с `wot-src` по [evidence-and-intake.md](evidence-and-intake.md); расхождение патча/build внутри одной мажорной версии не требует дополнительных действий. Повторно используйте подключение и установленный контекст, пока они не изменились.

Для каждой runtime-итерации:

1. Используйте уже собранный пакет; повторная сборка перед REPL не нужна. Отметьте начало теста временем, уникальным marker или доступной текущей позицией лога. Не вычитывайте историю ради получения cursor и не очищайте лог.
2. Примените обновлённый код способом, уже принятым в проекте, и убедитесь, что клиент исполняет именно его. Установка REPL agent не устанавливает пользовательский мод, а копирование нового пакета не обновляет уже импортированные модули. Если в проекте есть проверенный reload с корректной очисткой hooks/listeners, используйте его; иначе установите пакет и перезапустите выбранный тестовый клиент, когда это необходимо. Не создавайте hot-reload систему ради ускорения одной задачи и не вызывайте слепой `reload()`.
3. Проверьте изменённый сценарий коротким `wot_exec` или действием в UI. Read-only probe определения/типа/signature нужен для неизвестного API или сбоя; не повторяйте интроспекцию известного контракта перед каждым тестом. Для визуальной правки подтвердите результат screenshot и относящимся к нему state/log; сравнение до/после используйте, когда оно помогает оценить изменение.
4. Сделайте ограниченную выборку сообщений мода и ошибок за интервал теста по правилам ниже, проверьте ожидаемый результат и завершите итерацию. При сбое исправьте его и повторите затронутую проверку; не расширяйте прогон без конкретной причины.

При доступном REPL выполняйте относящиеся к задаче проверки самостоятельно. Не спрашивайте повторное разрешение на обычный probe, скриншот или проверку UI в уже выбранном тестовом контексте. Если пользователь просит только артефакт, отдайте сборку. Если REPL/клиент недоступен, отметьте runtime как непроверенный; не превращайте обычную правку в установку и настройку MCP без запроса.

Используйте `wot_mouse`/`wot_keyboard` только для воспроизводимого теста в рамках задачи в меню, replay, тренировочной комнате, тестовом режиме или «Полигоне». Не автоматизируйте gameplay и не отправляйте input в публичном бою. Не запускайте и не закрывайте чужую сессию без необходимости задачи; сохраняйте выбранный тестовый клиент между итерациями, если перезапуск не нужен. Закрывайте его через `wot_close_client`, когда это входит в scope; `wot_kill_client` используйте только после неудачи graceful close и с учётом потери несохранённого state.

`wot_exec` работает на main thread: не запускайте долгие циклы, blocking I/O, ожидание или тяжёлую обработку. Используйте маленькие probes и ограниченный timeout. Перед input-событием проверьте текущий экран и focus через screenshot/state. Скриншоты могут содержать никнеймы, чат и другие пользовательские данные — не публикуйте их автоматически.

## Логи: целевая выборка

Для быстрой обратной связи после действия используйте REPL-логи: последние N строк/записей с небольшим лимитом. Параметры берите из фактической MCP schema. Не обходите страницы по cursor до конца потока или пустого ответа и не запускайте постоянный polling.

Для большого поиска, истории загрузки или ошибки, уже ушедшей из хвоста, обращайтесь напрямую к `<game-root>/python.log` в корне выбранной установки игры. При доступе к файлу используйте `rg` по marker/prefix, имени модуля/ресурса и ошибкам с небольшим контекстом. Фильтруйте на стороне файловой системы; в контекст агента возвращайте нужные совпадения, а не весь файл. Не читайте большой файл через `wot_exec` в главном потоке клиента.

- Отделяйте текущий тест от старой истории по времени, marker или позиции файла. Ищите сообщения мода и ошибки/traceback отдельно: ошибка загрузки может возникнуть до первого сообщения мода.
- При найденной ошибке прочитайте полный относящийся к ней traceback и небольшой соседний контекст. Его строки не обязательно содержат префикс мода. Повторяющиеся одинаковые сообщения достаточно показать один раз.
- Если REPL-хвост не охватывает нужный эпизод, переходите к файлу. Если файл недоступен, укажите ограничение проверки; не компенсируйте это последовательным вычитыванием REPL-истории.
- Завершайте чтение после проверки ожидаемого результата и относящихся к сценарию ошибок. Расширяйте поиск только при конкретном сбое или отсутствии marker. Отсутствие ошибок в последних N строках не доказывает их отсутствие во всём логе.

## Что проверять

Smoke test первой загрузки, изменений bootstrap/lifecycle и готовности релиза; для обычной правки выбирайте затронутые пункты:

- package обнаружен loader-ом;
- entry завершился без traceback;
- ожидаемые subscriptions/registrations установлены один раз;
- feature выдаёт безопасный наблюдаемый marker;
- после действия нет новых ошибок;
- повторный вход в context не дублирует hook/listener.

Для patch migration добавьте probes изменившихся signatures и lifecycle state. Для Scaleform проверяйте затронутые Python registration, создание view и bridge; для Gameface — затронутые resource id, view/model, engine readiness, JS/Python commands и cleanup. Несколько разрешений/UI scale нужны при изменении адаптивного layout или проверке готовности релиза, а не после каждой правки текста/обработчика.

Предпочитайте replay для воспроизводимости. Если replay недостаточен, используйте тренировочную комнату, тестовый сервер или «Полигон». Записывайте точные шаги, карту/режим и момент ожидаемого поведения, чтобы следующий прогон был сопоставим.

Итоговое утверждение различайте явно:

- **source-backed** — решение основано на доступных исходниках с указанной версией;
- **exact-source-verified** — API подтверждён checkout той же версии/build;
- **build-verified** — compiler и package checks прошли;
- **load-verified** — клиент загрузил мод без новых ошибок;
- **behavior-verified** — целевой runtime scenario наблюдался;
- **visual-verified** — ожидаемое состояние интерфейса подтверждено screenshot и связанным runtime state;
- **cross-product verified** — предыдущие проверки отдельно прошли для каждой заявленной цели.
