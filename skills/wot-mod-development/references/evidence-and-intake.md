# Evidence gate и первичный intake

Читайте при первом входе в проект, смене цели или расследовании несовместимости. В следующих итерациях используйте уже установленный контекст; проверяйте только изменившиеся или неизвестные данные.

## Что определить до вопросов пользователю

Сначала осмотрите workspace и соседние явно связанные каталоги:

- есть ли готовый проект, `meta.xml`, `res/`, `mod_*.py`, build-скрипты и CI;
- есть ли `wot-src` в проекте или путь к нему в настройках редактора/build-скриптах;
- какие расширения и каталоги указывают на Python, AS3/Scaleform, Gameface или resource-only мод;
- есть ли логи, replay, описание ошибки и уже зафиксированная версия клиента.

Если нужен отчёт об окружении, используйте read-only `scripts/inspect_environment.py` из этого скилла. Это вспомогательный инструмент первичной настройки/диагностики, не обязательный шаг каждой сборки. Если известна версия, но нет доступа к установке игры, передайте её через `--target-version "v.X.Y.Z.W #BUILD"` вместо `--game-dir`.

## Минимальная карточка цели

Разрешите следующие поля; спрашивайте только отсутствующие:

| Поле | Почему оно важно |
| --- | --- |
| Product/owner | Wargaming WoT и Lesta «Мир танков» расходятся |
| Region/source data-branch | В `wot-src` каждый клиент/регион представлен отдельной data-веткой |
| Client version + build | Помогает оценить риск несовместимости, но не заменяет наличие исходников |
| Source path + branch + SHA | Делает каждое API-решение воспроизводимым |
| Новый/существующий проект | Определяет архитектурную свободу |
| UI stack | Определяет компиляторы, библиотеки и runtime-проверки |
| Runtime context | Ангар, бой и реплей имеют разные lifecycle и приложения |
| Execution topology | Windows, WSL, другая машина и доступность клиента/MCP меняют тестовый цикл |

Для universal-мода оформите по одной строке на каждую цель. Не объединяйте WoT и «Мир танков» в строку «совместимо» до отдельной проверки обоих клиентов.

## Как получить и проверить `wot-src`

Канонический источник: <https://github.com/wotstat/wot-src>. Ветка `main` содержит publisher-код и reusable workflow, а не данные игры. Для работы обязательно переключитесь на data-ветку целевого клиента:

| Цель | Data-ветка |
| --- | --- |
| World of Tanks — Europe | `wot-eu` |
| World of Tanks — North America | `wot-na` |
| World of Tanks — Asia | `wot-asia` |
| World of Tanks — China | `wot-cn` |
| World of Tanks — Common Test | `wot-common-test` |
| «Мир танков» — Россия | `mt-ru` |
| «Мир танков» — Public Test | `mt-public-test` |

Для свежего snapshot без лишней истории:

```bash
git clone --depth 1 --no-single-branch https://github.com/wotstat/wot-src.git
git -C wot-src switch <data-branch>
```

Проверяйте фактический список веток в remote/README: со временем он может расшириться. Не угадывайте ветку только по языку интерфейса.

Проверьте локально:

```bash
git -C <wot-src> status --short --branch
git -C <wot-src> rev-parse HEAD
git -C <wot-src> log -1 --format=%s
git -C <wot-src> branch -a --contains HEAD
```

Ожидайте каталоги как минимум:

```text
sources/res/scripts/client
sources/res/scripts/common
sources/res/scripts/client_common
```

В data-ветке также есть `.publication.json`: проверьте как минимум `branch`/`target`, `publisher`, `commit_subject`, `version_name`, `snapshot_created_at` и `snapshot_id`. `.version_name` хранит внутреннее имя версии snapshot, а для сопоставления публичной версии и build клиента используйте прежде всего `commit_subject`/сообщение коммита вида `X.Y.Z.W #BUILD`. В корне установки игры возьмите значение `<version>` из `version.xml`.

Сопоставление версии — это confidence signal, а не обязательный допуск к работе:

- точное совпадение версии и build даёт максимальную уверенность в найденных контрактах;
- в пределах одной мажорной версии другой минорный патч, микропатч или отличающийся/отсутствующий build некритичны: продолжайте с доступным `wot-src` без отдельного предупреждения и дополнительных проверок только из-за версии; это одинаково относится к версии из файловой системы и из WotStat REPL MCP;
- предыдущий крупный релиз тоже остаётся полезным источником структуры и аналогов, но требует явного предупреждения, поиска изменений и runtime validation;
- отсутствие исходного кода или необходимых script roots остаётся блокером.

Не ждите публикации исходников микропатча и не ищите точный snapshot только ради совпадения номера. Проверяйте затронутые API дополнительно при конкретных признаках несовместимости. Инспектор сообщает любое неточное совпадение как `warning`/`reduced`; если причина только в патче/build внутри одной мажорной версии, считайте это информационной отметкой и продолжайте без отдельного расследования.

Если нужен старый точный checkout, shallow clone может не содержать его. Сначала получите историю нужной data-ветки, затем найдите соответствующий коммит, не переключая молча общий рабочий каталог:

```bash
git -C <wot-src> fetch --unshallow origin <data-branch>
git -C <wot-src> log --all --format='%H %D %s' --grep='X\.Y\.Z\.W #BUILD'
```

Для параллельной работы с несколькими продуктами/патчами предпочтительны отдельные checkouts или `git worktree`. Не переносите автоматически решение между data-ветками. Исходники другой игры не закрывают обязательный source gate для заявленной цели; `main` также не закрывает его, потому что не содержит client/common script roots.

Если репозитория нет, помогите пользователю выбрать ветку и клонировать его. Предупредите, что репозиторий большой. Не добавляйте его содержимое в репозиторий мода; обычно `wot-src/` должен быть исключён из VCS и упаковки.

## Что считать доказательством API

Для нового или изменяемого игрового контракта найдите (ранее подтверждённые неизменившиеся сведения используйте повторно):

1. определение класса, функции, события или константы;
2. реальные вызовы и форму аргументов;
3. lifecycle: когда объект существует и когда уничтожается;
4. ближайший игровой аналог требуемого поведения;
5. различия между целевыми source commits, если задача касается миграции или нескольких продуктов.

Используйте `rg -n` по точным и соседним символам. Проверяйте не только определение, но и callers/subclasses. Для нативных объектов без `.py` используйте `stubs/` из того же snapshot или [WotStat REPL](https://github.com/wotstat/wotstat-repl), сохраняя source gate.

При миграции или нескольких целях полезна компактная таблица решений:

| Решение | Product/build | Source SHA | Файл/символ | Runtime evidence |
| --- | --- | --- | --- | --- |

Для обычной итерации отдельная таблица не нужна. Достаточно сохранять найденные пути/символы в контексте работы; не создавайте отчётный файл без необходимости задачи.

## Состояния gate

- **Ready:** script roots доступны, data-ветка соответствует цели, мажорная версия совпадает; расхождение минорного патча, микропатча или build допустимо.
- **Warning:** script roots доступны, но мажорная версия/data-ветка неизвестны или отличаются. Продолжайте, сообщите риск и компенсируйте его source diff, capability checks и runtime validation. Технический `warning` инспектора только из-за патча/build трактуйте по правилу выше.
- **Blocked:** исходников нет, путь недоступен либо отсутствуют необходимые client/common script roots. Допустимы только получение исходников, проверка окружения и общая архитектурная дискуссия.

Фраза пользователя «на последнем патче» не заменяет конкретную версию: версии двух продуктов могут быть разными. Однако неизвестная или отличающаяся версия сама по себе не должна останавливать работу при наличии пригодных исходников.
