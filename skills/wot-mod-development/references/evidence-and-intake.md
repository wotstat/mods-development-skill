# Исходники игры и выбор цели

Читайте, когда нужно найти исходники, выбрать data-ветку или расследовать несовместимость. Общий порядок работы и правила сопоставления версий — в [SKILL.md](../SKILL.md).

## Выбор цели

Определите продукт/регион и путь к его `wot-src` по запросу, файлам проекта и настройкам редактора. Уточняйте только то, без чего нельзя выбрать правильную цель или продолжить задачу. Не запрашивайте номер билда и полный паспорт окружения ради заполнения полей.

Если нужен отчёт об окружении, используйте read-only `scripts/inspect_environment.py` из этого скилла. Это вспомогательный инструмент первичной настройки/диагностики, не обязательный шаг каждой сборки. Если известна версия, но нет доступа к установке игры, передайте её через `--target-version "v.X.Y.Z.W #BUILD"` вместо `--game-dir`.

## Как получить и проверить `wot-src`

Канонический источник: <https://github.com/wotstat/wot-src>. Ветка `main` содержит publisher-код и reusable workflow, а не данные игры. Для работы обязательно переключитесь на data-ветку целевого клиента:

| Цель | Data-ветка |
| --- | --- |
| World of Tanks — Europe | `wot-eu` |
| World of Tanks — North America | `wot-na` |
| World of Tanks — Asia | `wot-asia` |
| World of Tanks — China | `wot-cn` |
| World of Tanks — Common Test | `wot-common-test` |
| «Мир танков» — Россия | `mt-ru` |
| «Мир танков» — Public Test | `mt-public-test` |

Для свежего snapshot без лишней истории:

```bash
git clone --depth 1 --no-single-branch https://github.com/wotstat/wot-src.git
git -C wot-src switch <data-branch>
```

Если нужной ветки нет в списке, проверьте remote/README. Не угадывайте ветку только по языку интерфейса.

Проверьте локально:

```bash
git -C <wot-src> status --short --branch
git -C <wot-src> log -1 --format=%s
```

Ожидайте каталоги как минимум:

```text
sources/res/scripts/client
sources/res/scripts/common
sources/res/scripts/client_common
```

Для обычной разработки достаточно правильной data-ветки и доступных исходников нужного API. Если нужно сопоставить версии, используйте сообщение коммита вида `X.Y.Z.W #BUILD` и `<version>` из `version.xml` в корне игры либо версию из REPL. В `.publication.json` для этого полезен `commit_subject`; `version_name` — внутреннее имя snapshot. SHA и остальные metadata исследуйте только для конкретной задачи миграции/диагностики.

Инспектор может сообщать неточное совпадение как `warning`/`reduced`; отметка только из-за патча/build не требует расследования по правилам [SKILL.md](../SKILL.md).

Если нужен старый точный checkout, shallow clone может не содержать его. Сначала получите историю нужной data-ветки, затем найдите соответствующий коммит, не переключая молча общий рабочий каталог:

```bash
git -C <wot-src> fetch --unshallow origin <data-branch>
git -C <wot-src> log --all --format='%H %D %s' --grep='X\.Y\.Z\.W #BUILD'
```

Для работы с несколькими продуктами/патчами используйте отдельные checkouts или `git worktree`, если нужно держать их одновременно.

Если репозитория нет, помогите пользователю выбрать ветку и клонировать его. Предупредите, что репозиторий большой. Не добавляйте его содержимое в репозиторий мода; обычно `wot-src/` должен быть исключён из VCS и упаковки.

## Исследование API

Читайте столько исходников, сколько нужно для понимания используемого контракта. Для константы достаточно определения; для подписки важны время жизни объекта и снятие обработчика; для неясных аргументов полезен реальный caller. Не проходите обязательный список определений, callers, subclasses и аналогов для каждого символа.

Ищите через `rg` по нужным символам. Для нативных объектов без `.py` дополняйте исходники `stubs/` из того же snapshot или runtime-интроспекцией через REPL.
