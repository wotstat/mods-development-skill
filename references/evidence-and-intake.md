# Evidence gate и первичный intake

Читайте этот файл перед реализацией, диагностикой или переносом мода.

## Что определить до вопросов пользователю

Сначала осмотрите workspace и соседние явно связанные каталоги:

- есть ли готовый проект, `meta.xml`, `res/`, `mod_*.py`, build-скрипты и CI;
- есть ли `wot-src` в проекте или путь к нему в настройках редактора/build-скриптах;
- какие расширения и каталоги указывают на Python, AS3/Scaleform, Gameface или resource-only мод;
- есть ли логи, replay, описание ошибки и уже зафиксированная версия клиента.

Используйте `scripts/inspect_environment.py` из этого скилла для воспроизводимого отчёта. Скрипт ничего не меняет. Если известна версия, но нет доступа к установке игры, передайте её через `--target-version "v.X.Y.Z.W #BUILD"` вместо `--game-dir`.

## Минимальная карточка цели

Разрешите следующие поля; спрашивайте только отсутствующие:

| Поле | Почему оно важно |
| --- | --- |
| Product/owner | Wargaming WoT и Lesta «Мир танков» расходятся |
| Region/source branch | В `wot-src` регионы представлены ветками |
| Client version + build | Помогает оценить риск несовместимости, но не заменяет наличие исходников |
| Source path + branch + SHA | Делает каждое API-решение воспроизводимым |
| Новый/существующий проект | Определяет архитектурную свободу |
| UI stack | Определяет компиляторы, библиотеки и runtime-проверки |
| Runtime context | Ангар, бой и реплей имеют разные lifecycle и приложения |
| Execution topology | Windows, WSL, другая машина и доступность клиента/MCP меняют тестовый цикл |

Для universal-мода оформите по одной строке на каждую цель. Не объединяйте WoT и «Мир танков» в строку «совместимо» до отдельной проверки обоих клиентов.

## Как проверить `wot-src`

Рекомендуемый источник: <https://github.com/izeberg/wot-src>. Документация WotStat указывает, что репозиторий обновляется по версиям клиента и использует ветки регионов: <https://docs.wotstat.info/guide/scripting/sources/>.

Проверьте локально:

```bash
git -C <wot-src> status --short --branch
git -C <wot-src> rev-parse HEAD
git -C <wot-src> log -1 --format=%s
git -C <wot-src> branch -a --contains HEAD
```

Ожидайте каталоги как минимум:

```text
sources/res/scripts/client
sources/res/scripts/common
sources/res/scripts/client_common
```

В корне обычно есть `.version_name`, но для сопоставления публичной версии клиента используйте прежде всего сообщение коммита вида `v.X.Y.Z.W #BUILD`. В корне установки игры возьмите значение `<version>` из `version.xml`.

Сопоставление версии — это confidence signal, а не обязательный допуск к работе:

- точное совпадение версии и build даёт максимальную уверенность в найденных контрактах;
- другой микропатч или отсутствующий build требует предупреждения и проверки затронутых symbols;
- предыдущий крупный релиз тоже остаётся полезным источником структуры и аналогов, но требует явного предупреждения, поиска изменений и runtime validation;
- отсутствие исходного кода или необходимых script roots остаётся блокером.

Если нужен точный checkout, попробуйте найти соответствующий коммит в истории, не переключая молча общий рабочий каталог:

```bash
git -C <wot-src> log --all --format='%H %D %s' --grep='v\.X\.Y\.Z\.W #BUILD'
```

Для параллельной работы с несколькими продуктами/патчами предпочтительны отдельные checkouts или `git worktree`. Ветку определяйте по целевому региону и `git ls-remote --heads`; не переносите автоматически решение с ветки `RU` на WG-регионы или обратно. WotStat сейчас рекомендует `RU` для «Мир танков», но фактический remote остаётся источником истины. Исходники другой игры не закрывают обязательный source gate для заявленной цели.

Если репозитория нет, помогите пользователю выбрать ветку и клонировать его. Предупредите, что репозиторий большой. Не добавляйте его содержимое в репозиторий мода; обычно `wot-src/` должен быть исключён из VCS и упаковки.

## Что считать доказательством API

Для каждого game-coupled изменения найдите:

1. определение класса, функции, события или константы;
2. реальные вызовы и форму аргументов;
3. lifecycle: когда объект существует и когда уничтожается;
4. ближайший игровой аналог требуемого поведения;
5. различия между целевыми source commits.

Используйте `rg -n` по точным и соседним символам. Проверяйте не только определение, но и callers/subclasses. Для нативных объектов без `.py` используйте сгенерированные stubs или Fuflo WoT REPL, сохраняя source gate.

В рабочем отчёте держите компактный ledger:

| Решение | Product/build | Source SHA | Файл/символ | Runtime evidence |
| --- | --- | --- | --- | --- |

Не обязательно коммитить эту таблицу в проект; она должна быть доступна в итоговом объяснении или существующем compatibility-документе проекта.

## Состояния gate

- **Ready:** script roots доступны, а ветка и версия подтверждены без известных расхождений.
- **Warning:** script roots доступны, но версия/build/ветка неизвестны или отличаются. Продолжайте, сообщите риск и компенсируйте его source diff, capability checks и runtime validation.
- **Blocked:** исходников нет, путь недоступен либо отсутствуют необходимые client/common script roots. Допустимы только получение исходников, проверка окружения и общая архитектурная дискуссия.

Фраза пользователя «на последнем патче» не заменяет конкретную версию: версии двух продуктов могут быть разными. Однако неизвестная или отличающаяся версия сама по себе не должна останавливать работу при наличии пригодных исходников.
